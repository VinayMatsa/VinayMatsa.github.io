CI/CD with Azure DevOps and GitHub Actions

VM Vinay Matsa 21 November 2026 3 min read

Power Platform pipelines (Level 6) give makers one-click deployments. When IT wants deployments that run from a repository, with approvals, tests and audit trails like the rest of their software, they use Azure DevOps or GitHub Actions with Microsoft's Power Platform build tools. The tasks call the same operations as pac.

The usual shape

  1. Export the unmanaged solution from development and unpack it into the repository (a commit others can review).
  2. Build: pack a managed zip from the repository and run solution checker on it.
  3. Release: import the managed zip into test with that environment's deployment settings; after approval, the same zip into production.

Signing in without a person

Pipelines sign in with an app registration (service principal) in Microsoft Entra ID, added as an application user in each environment with a security role that can import solutions. In Azure DevOps that becomes a service connection; in GitHub, variables and a secret. Prefer workload identity federation (no stored secret) where your tools support it.

Azure DevOps

# azure-pipelines.yml: export, check and store a solution
trigger: none
pool:
  vmImage: windows-latest
steps:
- task: PowerPlatformToolInstaller@2
- task: PowerPlatformExportSolution@2
  inputs:
    authenticationType: PowerPlatformSPN
    PowerPlatformSPN: Contoso-Dev        # service connection
    SolutionName: ContosoRequests
    SolutionOutputFile: $(Build.ArtifactStagingDirectory)/ContosoRequests.zip
- task: PowerPlatformChecker@2
  inputs:
    PowerPlatformSPN: Contoso-Dev
    FilesToAnalyze: $(Build.ArtifactStagingDirectory)/ContosoRequests.zip
    RuleSet: '0ad12346-e108-40b8-a956-9a8f95ea18c9'   # Solution checker rule set
- task: PublishPipelineArtifact@1
  inputs:
    targetPath: $(Build.ArtifactStagingDirectory)
    artifact: solution

GitHub Actions

# .github/workflows/export-solution.yml
name: Export solution to Git
on: workflow_dispatch
jobs:
  export:
    runs-on: windows-latest
    steps:
    - uses: actions/checkout@v4
    - uses: microsoft/powerplatform-actions/actions-install@v1
    - uses: microsoft/powerplatform-actions/export-solution@v1
      with:
        environment-url: ${{ vars.DEV_URL }}
        app-id: ${{ vars.CLIENT_ID }}
        client-secret: ${{ secrets.CLIENT_SECRET }}
        tenant-id: ${{ vars.TENANT_ID }}
        solution-name: ContosoRequests
        solution-output-file: out/ContosoRequests.zip
    - uses: microsoft/powerplatform-actions/unpack-solution@v1
      with:
        solution-file: out/ContosoRequests.zip
        solution-folder: src/ContosoRequests
        solution-type: Unmanaged
        overwrite-files: true

The ${{ }} parts read repository variables and secrets, so no credentials sit in the file.

Flow-specific points

  • Flows import off if their connection references have no connection. Deployment settings fix that, or a post-import step turns them on.
  • The account that owns imported flows is the pipeline's identity unless you change it. Plan who should own production flows (Level 6, service accounts).
  • Run a smoke test after release: trigger a test flow and check its run succeeded.
New to this? Start from the basics optional

CI/CD: continuous integration and delivery. Every change is built, checked and deployed by an automated pipeline instead of by hand.

YAML: the text format used to describe pipeline steps.

Service principal: an identity for an app or pipeline, not a person.

Build it step by step optional
  1. Create an app registration and add it as an application user in dev, test and prod.
  2. Create the service connection (Azure DevOps) or variables and secret (GitHub).
  3. Start with an export pipeline that unpacks into the repository. Run it manually.
  4. Add a build pipeline that packs a managed zip and runs the checker.
  5. Add release stages for test and production, with an approval before production.

Common mistakes

  • Giving the service principal System Administrator everywhere because it's easier.
  • Building a different zip for production than the one that was tested. Promote the same artifact.
  • Forgetting that flows can arrive turned off.
