SQL Server and the on-premises data gateway

VM Vinay Matsa 21 November 2026 3 min read

Many business systems keep data in SQL Server or Azure SQL Database. The SQL Server connector (premium) reads and writes rows, runs queries and calls stored procedures. No live demo here: it needs a database.

Cloud or on-premises?

WhatA connector for SQL databases; on-premises servers are reached through a gateway.
WhyLine-of-business data often lives in SQL.
DemoOrders over a minimum amount for a given status.

How the flow reaches the database

Where is the database?
Azure SQL
Directly (Entra ID or SQL auth; allow Azure services in the firewall)
In your network
Flow → cloud → on-premises data gateway (connects out)
→ SQL Server

The actions

ActionUse
Get rows (V2)Filter, order, top, select; paging like Get items
Insert / Update / Delete row (V2)Single-row writes (needs a primary key)
Execute a SQL query (V2)Your own SELECT with parameters (check known limitations)
Execute stored procedure (V2)Logic in the database, cleanest
SELECT OrderId, Customer, Amount
FROM dbo.Orders
WHERE Status = @status AND Amount > @minAmount

Pass values as parameters, never by joining them into the query text.

Gateway basics

RuleWhy
Install on an always-on server that reaches the databaseA sleeping laptop stops every flow
Same region as your environment; add a second cluster memberSpeed and availability
Gateway admins control who creates connectionsOne gateway serves many flows, apps and reports
New to this? Start from the basics optional

Primary key: the column that uniquely identifies a row.

Stored procedure: saved SQL you call with parameters.

Common mistakes

  • SQL text built from user input.
  • Gateway on a personal machine.
  • Reading a whole table to find one row.
