Batch operations and changesets

VM Vinay Matsa 21 November 2026 3 min read

When a flow writes many rows, the usual pattern is a loop with one Create or Update per item. Every pass is a request and a round trip to the service. Batching sends several operations in one call. Changesets go further: they make a group of writes all or nothing.

Ways to reduce write calls

ApproachWhat it doesWhen to use it
Prepare data before the loopUse Select and Filter array so the loop only does the write, with nothing else inside itAlways. It is the cheapest win.
Loop concurrencyRuns several passes at once (up to 50)Independent writes where order doesn't matter. Faster, but the request count is the same.
Dataverse changesetGroups Add, Update and Delete row actions into one transactionRows that must stay consistent with each other
Batch request through HTTPOne $batch call to the Dataverse Web API or SharePoint REST API holding many operationsLarge volumes, when you are comfortable building the request body
Process outside the flowHand the file to a dataflow, an import, or a stored procedureThousands of rows on a regular schedule

What a changeset gives you

Normally, if the third of five writes fails, the first two stay saved and the data is half-updated. Inside a changeset, Dataverse runs the writes as one transaction. If any of them fails, all of them are rolled back. Typical uses: creating an order with its order lines, or moving a balance from one record to another.

Points to know:

  • A changeset holds only Dataverse Add a new row, Update a row and Delete a row actions.
  • You can't use an output of one action in a later action of the same changeset, because nothing is saved until the end.
  • Microsoft lists changesets as not yet supported in the new designer, so build or edit them in the classic designer.

This page has no demo screenshot for that reason: the environment used for these articles runs the new designer, and the documented limitation applies.

New to this? Start from the basics optional

Batch: many operations sent together in one HTTP call. Each one can still succeed or fail on its own.

Transaction: a group of changes that is saved together or not at all.

Rollback: undoing the changes already made in a transaction when a later one fails.

Build it step by step optional
  1. Switch to the classic designer for the flow (Microsoft's changeset page explains how).
  2. Add the action Perform a changeset request from the Dataverse connector.
  3. Inside it, add the Add a new row, Update a row or Delete a row actions you need.
  4. Fill in each action with values from before the changeset, not from actions inside it.
  5. Test with one bad value on purpose and confirm that none of the rows were saved.

Common mistakes

  • Expecting a batch to be a transaction. Only a changeset rolls back; plain batches don't.
  • Turning on high concurrency for writes that depend on each other, such as running totals.
  • Referencing the ID of a row created earlier in the same changeset. It doesn't exist yet.
