Harnesses in Copilot Studio: the runtime behind every agent

VM Vinay Matsa 8 October 2026 2 min read

The harness you use in Copilot Studio is becoming an important design decision, because it affects the billing, features and capabilities of what you build.

Update (November 2026): since the original post, Microsoft Learn has renamed the harnesses. It now describes the Microsoft Copilot harness (reasoning-heavy, multi-step work), the Customer Conversation harness (customer service over voice and chat) and the standard harness (rule-based agents and agent flows). The principles below still hold; check the harnesses overview for the current names and details.

Start from the root

You design the agent. The model provides reasoning and text. The harness is the runtime between the two: it decides when to call the model, what to send it, how to interpret what comes back, and which tools to call. Same model, different harness, different behaviour and cost.

The harnesses as I compared them in October 2026

  • The reasoning harness (then called the GitHub Copilot harness, a Copilot Studio framework, not the GitHub Copilot service): takes a goal, breaks it into steps, calls tools across connectors, knowledge, MCP and connected agents, and adjusts when a step fails. Works with Office and PDF files and supports skills and memory.
  • The standard harness: a dependable runtime for rule-based agents, structured conversations and agent flows. You define the topics, prompts and paths, so behaviour stays predictable.
  • The Copilot Chat harness: extends Microsoft 365 Copilot Chat with enterprise knowledge (declarative agents).

Points that matter when choosing

  • Connectors or MCP servers alone don't require the reasoning harness.
  • Reasoning models and some newer agentic features are only available on the reasoning harness.
  • A more capable harness can overwork a simple problem, raising credit use and latency without improving the result.
  • You choose the harness when you create the agent. Moving between harnesses is a re-architecture, not a setting.

From my own lab

My agents are short, bounded and rule-based. They use topics, agent flows and a child agent, so the standard harness is the right fit. The activity map in the test pane shows the harness at work: interpreting tool intent, preparing inputs, running the tool and processing the result.
