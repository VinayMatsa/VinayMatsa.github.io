Data loss prevention (DLP) policies

VM Vinay Matsa 21 November 2026 3 min read

Admins use data policies (often called DLP policies) to stop company data flowing to places it shouldn't. A policy decides, per environment, which connectors are allowed and which may be combined in one flow. As a maker you don't set these, but you will meet them, usually as an error when you save or turn on a flow.

What it looks like

The flow saved but wouldn't turn on. Nothing in the flow is wrong; the environment doesn't allow that connector.

Classic policies: three groups

GroupMeaning
BusinessConnectors for company data. They can be used together.
Non-BusinessConnectors for personal or other data. They can be used together, but not with Business ones in the same flow.
BlockedCan't be used at all.

New connectors land in the policy's default group, which is Non-Business unless the admin changes it.

Advanced connector policies

The error above names an Advanced Connector Policy. Microsoft describes these as the next generation: instead of three groups they use a strict allowlist, and every connector that isn't explicitly allowed is blocked.

New to this? Start from the basics optional

Connector: the wrapper around a service (SharePoint, Outlook, HTTP) that gives a flow its actions.

Data policy: admin rules that apply to one or more environments, or to all of them.

What to do as a maker

  • Read the error: it names the policy and the connector.
  • Check whether another, allowed connector can do the job.
  • If the connector is truly needed, ask your admin, with the business reason and the environment name.
  • Build in an environment whose policy matches what production will allow, so there are no surprises at deployment.

Tenant isolation

Data policies control which connectors may be used. Tenant isolation controls where they may connect. It is off by default, so a connector that signs in with Microsoft Entra ID can connect to another organisation's tenant if the user has valid credentials there. With tenant isolation on, connections to and from other tenants are blocked, apart from tenants the admin adds to an allow list.

If a flow that reads another company's SharePoint suddenly can't connect, tenant isolation is a likely cause. It is an admin setting in the Power Platform admin center, not something a maker can change.

Common mistakes

  • Assuming the flow is broken and rebuilding it. The policy is the cause.
  • Developing in an environment with looser rules than production.
  • Mixing a business connector (SharePoint) with a non-business one (a personal mail service) in one flow.
