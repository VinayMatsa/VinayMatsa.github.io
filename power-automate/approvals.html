Approvals

VM Vinay Matsa 21 November 2026 4 min read

The Approvals connector adds a human decision to a flow. Start and wait for an approval sends a request (by email, in Teams and in the Approvals centre), pauses the flow, and continues when the approver responds, with their decision and comments as outputs.

The approval step

SettingDemo value
Approval typeApprove/Reject - First to respond
TitleContoso: approve New laptop for design team (1,450)
Assigned toThe approver's email address
DetailsRequested by the Design team. Priority: High.

After it, read the result:

body('Start_and_wait_for_an_approval')?['outcome']
PieceWhat it does
body('Start_and_wait_for_an_approval')The approval's result once someone responds.
?['outcome']Approve or Reject for the basic types. Use it in a Condition.
coalesce(first(body('Start_and_wait_for_an_approval')?['responses'])?['comments'], 'No comment')

That second expression reads the first approver's comment, with a fallback when none was given (the Level 2 null-handling pattern).

When a policy blocks it

In the demo environment the flow could not even be turned on:

This is a data policy set by an administrator. This one is an advanced connector policy: it blocks every connector that is not on an allow list, so a connector that works in one environment can be refused in another. Nothing in the flow is wrong; the fix is a conversation with the Power Platform admin, who can allow the connector for the environment. Level 6 covers data policies in depth.

Before you build: check which connectors your target environment allows. Discovering a blocked connector after the build costs far more than asking first.
New to this? Start from the basics optional

Approvals centre: the Approvals page in Power Automate (and the Approvals app in Teams) where people see and answer requests.

Wait: the flow pauses for up to 30 days. If nobody responds, the run times out and fails, so plan a reminder or escalation.

Data policy (DLP): an admin rule about which connectors can be used, and which can be used together.

Build it step by step optional
  1. Create an instant flow and add Start and wait for an approval (Approvals).
  2. Choose Approve/Reject - First to respond, enter a Title, your own email in Assigned to, and some Details.
  3. Add a Condition: outcome is equal to Approve.
  4. In each branch add a Compose (or a Teams message) saying what happened.
  5. Save and turn the flow on. If you see an Admin data policy message, ask your admin which connectors are allowed in that environment.
  6. Test, then approve from the email, Teams or the Approvals page, and watch the run continue.

Timeouts and approvers from a list

When nobody responds. An approval waits until someone answers. To stop waiting, open the approval action's Settings and set Timeout, for example P7D for seven days. Then add a step set to run after the approval has timed out: update the request's status to Expired, tell the requester, and end the run with Terminate (Cancelled). Without a timeout the run simply stops when it reaches the 30-day limit for a run.

Choose approvers from data, not from the flow. Keep an Approvers list with columns such as Product and Approver email. In the flow:

  1. Get items from Approvers with a filter query: Product eq 'Laptops'.
  2. Select just the email: item()?['ApproverEmail'].
  3. Put join(body('Select'), ';') in the approval's Assigned to.

When an approver changes, the business updates the list and the flow is not touched.

Common mistakes

  • No plan for no response. Add a parallel branch with a Delay and a reminder, or set the action's timeout in its settings.
  • Assigning to a person by name in text. Use email addresses, separated by semicolons.
  • Not saving the decision anywhere. Write the outcome and comments back to the list or table so there's a record.
