The Dataverse security model: who sees what

VM Vinay Matsa 12 October 2026 2 min read

Every canvas app, model-driven app and Power Automate flow on Dataverse runs on one security model. It decides which records a user can open and which fields stay hidden.

Start from the root

Dataverse stores data in tables made of rows (records) and columns (fields). Security answers two questions for every user and every row: can they reach this row at all? and if so, which columns can they see? Apps don't decide this; Dataverse does, so the same rules apply whether someone uses an app, a flow or the API.

The pieces

PieceWhat it does
Business unitsGroup users, like departments. Every user belongs to exactly one.
Security rolesDecide which actions (create, read, write, delete, append, assign, share) a user can do on each table.
Access levelsDecide how wide each privilege reaches: User, Business Unit, Parent: Child Business Units, or Organization.
TeamsGive a role to a group of users at once.
SharingGrants access to one specific row, as an exception.
Hierarchy securityLets managers see their reports' rows.
Column securityHides sensitive columns inside rows a user can otherwise see.

Recommended approach

  • Start with the narrowest access level that works.
  • Assign roles to teams, not user by user.
  • Use sharing only for exceptions.
  • Use column security for fields like salary or medical notes.

Important to know

  • Roles add up. A user gets the broadest access from all their roles and teams combined; one generous role undoes careful ones.
  • System Administrator can see all data, not just configuration. Don't hand it out for convenience.
  • Column security never grants a row. Row access must come first; column security only narrows it.
