From the root: what is a topic?

WhatA topic is an authored conversation path: questions, messages, conditions, cards, and calls to flows or prompts, drawn on a canvas.
WhySome steps must happen in a fixed order every time (verify, then review, then create). A topic guarantees that order; the AI can't skip a step.
DemoNew Ticket: verify → describe → AI triage → review card → create.
TopicJobFlows it calls
Identify CustomerVerify by email + order/customer number, or registerFind Customer, Register Customer
New TicketAI triage, review card, duplicate check, createList Customer Orders, Create Ticket, Add Customer Reply
Warranty ClaimSerial, purchase date, fault, technician summary, RMARMA Process
Check Ticket StatusStatus, SLA, latest update, timeline; reply or escalateGet Ticket Details, Add Customer Reply
Track an OrderThe customer's own orders and trackingList Customer Orders
Rate a Ticket1–5 satisfaction score and commentRecord CSAT
EscalateHand to a person, safety casesEscalate Ticket, Create Ticket
Main Menu, Greeting, Goodbye, Thank you, Start OverConversation housekeeping—

The trigger: “The agent chooses”

The description is written for the orchestrator, like a routing rule: Use when a customer reports a problem they want logged… that is not a warranty repair claim, for example a late, lost or damaged delivery… Naming what a topic is not for stops it competing with Warranty Claim.

Topic inputs: filled from the conversation

inputs:
  - kind: AutomaticTaskInput
    propertyName: IssueDescription
    description: The customer's problem in their own words (what happened, when,
      and what they want), if they have already described it. Leave empty if they
      only asked to raise a ticket.
    shouldPromptUser: false

How IssueDescription was filled

Alex's first message already describes the problem
The orchestrator reads the input's description and extracts the matching text
Is it blank or under 20 characters?
Yes
Topic asks: Please describe the problem…
No
Skip the question; Alex isn't asked twice

shouldPromptUser: false means the orchestrator won't ask for it; the topic decides with its own check. This is how one topic handles both “raise a ticket” and a full description in the first message.

Topic variables vs global variables

ScopeLivesVink examples
Topic.Only while that topic runsTopic.Description, Topic.Subject, Topic.Priority, Topic.TicketNumber
Global.The whole conversation, across topicsGlobal.CustomerVerified, Global.ContactId, Global.CustomerEmail, Global.IsVIP

Why verification is global

Identify Customer sets Global.CustomerVerified = true
Later, Alex asks for the status of TKT-1020
Check Ticket Status runs Identify Customer, which sees the flag and ends at once: no second verification

Entities: recognising ORD-, TKT- and SN- numbers

OrderNumber   kind: RegexEntity   pattern: (?i)ORD-\d{5}
TicketNumber  kind: RegexEntity   pattern: (?i)TKT-\d{4,12}
SerialNumber  kind: RegexEntity   pattern: (?i)SN-[A-Z]{3}-\d{5}

What each pattern accepts

EntityMatchesDoesn't match
OrderNumberORD-10421 ord-10421ORD-421
TicketNumberTKT-1020TKT-12
SerialNumberSN-LTP-48213SN-48213

(?i) makes them case-insensitive.

Warranty Claim asks for the serial with the SerialNumber entity, so a typo is re-asked by the topic instead of being sent to a flow.

New to this? Start from the basics optional

Node: one step on a topic canvas.

Entity: a type of value the agent can recognise in text, like an email or a regex pattern.

Power Fx: the formula language used in topics (=Global.CustomerVerified = true).

Common mistakes

  • Topic descriptions that overlap.
  • Global variables for values that belong to one topic.
  • Asking again for something the customer already said: use topic inputs.
  • Free-text questions for structured IDs: use a regex entity.
