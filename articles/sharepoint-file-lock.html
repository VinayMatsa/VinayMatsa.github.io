SharePoint file lock errors in Power Automate

VM Vinay Matsa 1 May 2026 2 min read

Ever hit Microsoft.SharePoint.SPFileLockException with HTTP 400 or 423? It usually happens when a flow moves or updates a file while SharePoint still holds a lock on it.

Start from the root

SharePoint locks a file while something is working with it, so two changes can't collide and corrupt it. Locks come from a file being created or uploaded, a person editing it in Office, or a previous connector action that hasn't fully released it. Locks are temporary. The problem is timing: a flow runs actions faster than SharePoint releases them.

Why flows hit it

  • Back-to-back actions on the same file (create, then immediately update properties or move).
  • Parallel branches or loops touching the same file.
  • Someone has the file open in the desktop app.

The retry pattern

Power Automate can't unlock a file. It can only wait and try again safely:

  1. Initialise a boolean variable done = false.
  2. Do until done is true (with a sensible count and timeout limit).
  3. Inside: the file action, then a Set variable done = true that runs only if the action succeeded.
  4. A Delay (for example 30 seconds) configured to run after the action failed.

Exit the loop only after a successful run, and fail clearly if the limit is reached. The built-in retry policy helps for some errors, but a lock can last longer than its intervals, so the explicit loop is more reliable. The Learn section covers Do until loops and configure run after.

Remember: the goal isn't to beat the lock but to wait it out safely, with a limit.
