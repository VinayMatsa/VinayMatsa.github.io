SQL Server and the on-premises data gateway

VM Vinay Matsa 21 November 2026 3 min read

Many business systems keep their data in SQL Server or Azure SQL Database. The SQL Server connector (premium) reads rows, inserts and updates them, runs queries and calls stored procedures. No live demo here, because it needs a database; the patterns below are what you'd build.

Cloud or on-premises?

DatabaseHow the flow reaches it
Azure SQL DatabaseDirectly over the internet. Sign in with Microsoft Entra ID or SQL authentication, and allow Azure services in the server firewall.
SQL Server in your own networkThrough an on-premises data gateway: a Windows service installed inside your network that relays requests. The cloud never connects in; the gateway connects out.

The actions

  • Get rows (V2): with Filter Query (OData), Order By, Top Count and Select Query. Uses paging like SharePoint's Get items.
  • Insert row (V2), Update row (V2), Delete row (V2): the table needs a primary key.
  • Execute a SQL query (V2): your own SELECT with parameters. Check the connector's known limitations for your authentication type before relying on it.
  • Execute stored procedure (V2): the cleanest way to run logic in the database and return results.

Pass values as parameters, never by joining them into the query text:

SELECT OrderId, Customer, Amount
FROM dbo.Orders
WHERE Status = @status AND Amount > @minAmount

Gateway basics

  • Install it on a server that is always on and can reach the database, not on a laptop.
  • Install it in the same region as your environment if you can, and add a second machine to the gateway cluster for high availability.
  • The gateway is shared: one gateway serves many flows, apps and Power BI reports. Gateway admins control who may create connections on it.
New to this? Start from the basics optional

SQL: the language databases understand. SELECT reads, INSERT adds, UPDATE changes.

Primary key: the column that uniquely identifies a row.

Stored procedure: a saved, named piece of SQL that you call with parameters.

Build it step by step optional
  1. Ask the database owner for a login with only the permissions the flow needs.
  2. For an on-premises server, install the data gateway and register it in the same region as your environment.
  3. Create a SQL Server connection (choose the gateway for on-premises).
  4. Use Get rows with a Filter Query for reads and a stored procedure for anything complex.
  5. Use connection references and environment variables for the server and database names, so the flow moves between environments.

Common mistakes

  • Building SQL text with user input. Use parameters or stored procedures.
  • Running the gateway on a personal machine that sleeps.
  • Reading a whole table to find one row. Filter on the server.
